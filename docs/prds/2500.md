### **Ken**
"Architecturally, this requires a fundamental upgrade from your linear 'Shoebox' workflow to a highly concurrent, event-driven mesh.



Here is **Part 2 of the PRD: Technical Specifications & DAG Architecture**.

**1. The Ingress Layer: Quiltt API vs. Stripe**
* **Spec:** We use the **Quiltt API** (which aggregates Plaid, MX, and others) as our universal data pipe. Stripe is only useful for e-commerce revenue; Quiltt gives us access to 10,000+ US banks for complete expense tracking.
* **Execution:** You write a Go cron job (`worker.ingest.bank_feed`). Every night at 00:00 EST, it pulls the `delta` (new transactions) from the Quiltt `/transactions` endpoint for all connected client accounts.

**2. The Data Schema (Postgres)**
You must upgrade your database to handle asynchronous state:
* `transaction_id` (UUID)
* `raw_description` (String, e.g., "SQ *HOME DEPOT")
* `amount` (Float)
* `predicted_account` (String, mapped to COA)
* `confidence_score` (Float, 0.0 to 1.0)
* `status` (Enum: `pending_ai`, `auto_reconciled`, `pending_client`, `resolved_by_client`)

**3. The Toro Workflow (The Core DAG)**
* **Node 1: LLM Classifier Primitive:** Go passes the raw Quiltt JSON to GPT-4o-mini. The prompt includes the client's historical COA. The LLM returns the `predicted_account` and a `confidence_score`.
* **Node 2: The Routing Switch:**
    * *Condition A (Score > 0.90):* Go updates Postgres `status = auto_reconciled`. End of DAG.
    * *Condition B (Score < 0.90):* Go updates Postgres `status = pending_client` and triggers Node 3.
* **Node 3: The Twilio Exception Primitive:** Go spawns a goroutine that formats a dynamic SMS: *'Hi [Client], a $400 charge from Amazon cleared yesterday. What expense category does this belong in?'*
* **Node 4: The Webhook Listener:** The DAG suspends. When the Twilio webhook receives the client's SMS reply, Go wakes up, uses a tiny LLM to extract the intent from the text, maps it to the COA, updates the DB to `resolved_by_client`, and closes the loop.

This architecture is unshakeable. It shifts the burden of work entirely onto the APIs and the end-client, leaving the CPA in a state of pure observation."
