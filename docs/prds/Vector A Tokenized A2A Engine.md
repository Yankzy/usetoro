## 1. Executive Summary & Objective

The **Vector A** pivot transforms our outbound email infrastructure into a structured **Agent-to-Agent (A2A) Messaging & Negotiation Network**. We are moving away from traditional synthetic cold outreach and warmup techniques, pivoting entirely to authentic utility traffic. 

In this new model, the internal event bus (NATS) serves as a high-speed, asynchronous transport layer for semantic agent negotiations, completely bypassing external email networks. The defining mechanic is a **Sender-Pays-All** token economy: the initiating agent pays for the LLM token consumption on **both** sides of the interaction. Receiving companies host "Gatekeeper Agents" that register their capabilities with **Almanac** (our central discovery registry), parse inbound pitches, verify constraints, negotiate, and auto-reply without bearing the inference costs.

---

## 2. Target Personas & Stakeholders

| Role | Key Responsibilities & Objectives |
| --- | --- |
| **Initiator (Sender A)** | Initiates the conversation, seeking to pitch a service, buy software, or negotiate a deal. Pays the token inference costs for both their outbound agent and the recipient's Gatekeeper agent. |
| **Gatekeeper (Recipient B)** | Receives the inbound pitch. Uses a strict, user-defined ruleset (Gatekeeper Config) to evaluate the pitch, verify budgets/compliance, and auto-reply. Accrues zero token costs. |
| **Toro Platform** | Orchestrates the message transport, maintains the cross-tenant ledger, and enforces semantic circuit breakers to prevent spam/abuse loops. |

## 3. End-to-End Operating Workflow

```
[ Sender A Agent ] ──► Drafts Pitch & Authorizes Token Budget
        │
        ▼
[ Almanac Registry ] ─► Sender queries Almanac to discover B's Gatekeeper NATS Inbox
        │
        ▼
[ NATS Event Bus ] ──► Routes internal A2A payload directly to Recipient B's Inbox
        │
        ▼
[ Toro Gatekeeper ] ─► Parses payload, loads B's agent_configurations constraints
        │
        ▼
[ Cross-Tenant Burn ] ─► Deducts B's LLM generation cost from A's wallet
        │
        ▼
[ Gatekeeper LLM ] ──► Evaluates pitch against B's rules and generates response
        │
        ▼
[ NATS Event Bus ] ──► Routes reply directly back to Sender A
```

## 4. Key Functional Requirements

### Module 1: Cross-Tenant Burn Authorization (Ledger Upgrade)
* **Single-Payer Micrion Ledger:** Upgrade `toro_core.wallet_transactions` to authorize and execute burns across tenant boundaries.
* **Pre-Authorization Lock:** Before Recipient B's Gatekeeper invokes the LLM, the system must verify Sender A has sufficient Micrion balance and lock the estimated budget.
* **Cost Attribution:** The `toro_core.llm_turn_metrics` table must accurately attribute the output token costs generated by Tenant B's agent back to Tenant A's `conversation_session`.

### Module 2: Almanac Discovery & NATS Transport
* **Almanac Registry:** Agents register their DID, capabilities, and NATS Inbox subject with the central Almanac registry. Sending agents dynamically query Almanac to discover the correct Gatekeeper for their target tenant before dispatching.
* **Supply/Demand Telemetry:** The Almanac server must emit telemetry events for failed lookups (e.g., when an Initiator queries for a capability that returns zero Gatekeepers). This tracks market gaps and unmet supply/demand across the network.
* **A2A Payload Schema:** Leverage the existing TAP `core.Envelope` structure. `SenderDID` and `ReceiverDID` natively handle agent identity, and `ConversationID` handles thread tracking. Negotiations will use standard FIPA performatives (`PROPOSE`, `ACCEPT_PROPOSAL`, `REJECT_PROPOSAL`) defined in `tap/pkg/core/verbs.go`.

### Module 3: Gatekeeper Configurations
* **Dynamic Constraint Engine:** Leverage the existing `toro_core.agent_configurations` table. Gatekeeper rules (e.g., "Auto-reject software > $500/mo") will be stored as structured JSON within the `metadata` column.
* **Dual-Persona Context Injection:** The `ContextBuilder` must seamlessly inject the Gatekeeper's rules into the LLM system prompt when processing inbound A2A requests.

### Module 4: Anti-Gaming & Circuit Breakers
* **Semantic Loop Prevention:** Implement middleware to track thread turns. If a negotiation exceeds a predefined turn threshold without reaching a terminal state (deal/rejection), the system automatically aborts to prevent prompt-looping and wallet drain.
* **Agent Rate Limiting:** Implement spam traps at the `X-A2A-Agent-ID` level to prevent malicious Initiators from flooding Gatekeepers.

---

## 5. Non-Functional Requirements

* **Zero-Cost Receiver Guarantee:** Ensure airtight isolation in the billing layer so that Tenant B is absolutely never charged for an inbound pitch initiated by Tenant A.
* **Low-Latency Handoffs:** Because we bypass SMTP, the internal NATS to LLM invocation pipeline should execute in under 1 second to maintain rapid, real-time agent negotiations.

---

## 6. Implementation Roadmap

1. **Phase 1: Foundations (Ledger & Transport)**
   - Implement the Cross-Tenant Burn mechanism.
   - Wire the Gatekeeper to accept TAP `core.Envelope` messages and FIPA performatives.
   - Build NATS internal routing workers for A2A handoffs.
   
2. **Phase 2: Core Loop (Gatekeeper Agent)**
   - Expose Gatekeeper configuration UI and map it to `toro_core.agent_configurations`.
   - Update `ContextBuilder` to inject Gatekeeper logic.
   - Wire LLM turn metrics to the new Cross-Tenant Burn authorization.

3. **Phase 3: Security & Polish**
   - Implement semantic circuit breakers.
   - Deprecate legacy cold email (Mailpool warmup) infrastructure.
