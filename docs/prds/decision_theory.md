# Product Requirements Document (PRD)

## Layer 3: Recovery Policy Engine (Action Selection)

**Status:** Draft v1.0  
**Owner:** Runtime & AI Infrastructure Engineering  
**Audience:** Runtime Engineering, AI Infrastructure, ASE Core  

---

## 1. Objective

Implement the runtime framework for **Layer 3: Recovery Policy Engine** (also known as the Action Selection Engine) within the Autonomous Semantic Engine (ASE).

While Layer 1 (Shannon Entropy) measures uncertainty to determine *if* a node can proceed, Layer 3 determines *what action to take* when a node cannot proceed. This document defines the requirements for selecting the optimal recovery action for nodes in a `HOLD` state by evaluating expected success, latency, and operational cost, thus introducing Decision Theory into the ASE.

---

## 2. Problem Statement

Currently, the ASE utilizes Shannon Entropy to evaluate state. When entropy exceeds a threshold, the node enters a `HOLD` state. 

Historically, this transition meant the workflow simply stopped or immediately dispatched a generic alert (e.g., an email to the client). This approach lacks intelligence and optimization because:
1. **Conflating State with Strategy:** Shannon Entropy is a measure of state certainty, but it is incorrectly being used to dictate singular recovery actions.
2. **Suboptimal Recovery Paths:** Immediate escalation (like asking a CPA or sending an email) is highly expensive in terms of time and human capital, whereas cheaper alternatives (like searching local document stores or waiting for a concurrent node to finish) are ignored.
3. **Lack of Cost-Benefit Analysis:** The system cannot differentiate between a fast, cheap action with low probability of success versus a slow, expensive action with guaranteed success. 

---

## 3. Design Principles

The Recovery Policy Engine enforces a strict boundary between state evaluation and action selection:

1. **Clean Separation of Concerns:**
   - **Shannon Entropy** evaluates state: *"Am I certain enough to proceed?"*
   - **Recovery Policy Engine** evaluates strategy: *"What action reduces my uncertainty at the lowest cost?"*
2. **Cost-Based Optimization:** Recovery actions are not randomly selected. They are evaluated as an optimization problem maximizing expected value over cost and latency.
3. **Progressive Escalation:** The engine should always attempt the most efficient (fastest/cheapest) internal actions before escalating to high-latency external actions (emails, human review).
4. **Decoupled Execution:** The decision to take an action (e.g., aggregating missing documents into a single email at the end of a DAG) is a strategic choice, completely distinct from the entropy score that caused the initial HOLD.

---

## 4. Mathematical Modeling of Action Selection

### 4.1 Action Space ($A$)

When a node enters `HOLD`, the engine evaluates a set of possible recovery actions $A = \{a_1, a_2, \dots, a_n\}$. 

Example actions for a missing invoice:
- $a_1$: Query the internal document database.
- $a_2$: Query the email archive.
- $a_3$: Defer (wait for a concurrent node to produce evidence).
- $a_4$: Send an automated request to the client (aggregated at the end of the workflow).
- $a_5$: Escalate to human review.

### 4.2 Cost Function ($C$)

Each action $a \in A$ has an associated multidimensional cost $C(a)$:
- **Computational Cost:** Tokens consumed, database loads.
- **Latency Cost:** Expected time to resolution (milliseconds vs. days).
- **Human Capital Cost:** Engineering, CPA, or Client time required.

### 4.3 Expected Value ($EV$)

The engine selects the action that maximizes Expected Value ($EV$), defined as the probability of success $P(S|a)$ weighted by the Expected Information Gain ($ExpectedIG$), minus the Cost $C(a)$:

$$EV(a) = \left[ P(S|a) \times ExpectedIG(a) \right] - C(a)$$

**Example Evaluation:**
| Action ($a$) | Cost ($C$) | Prob. of Success ($P$) | Latency | Evaluation |
| :--- | :--- | :--- | :--- | :--- |
| $a_1$: Search document store | Very Low | 70% | 100 ms | **High EV** (Execute First) |
| $a_2$: Search email archive | Low | 20% | 500 ms | **Medium EV** |
| $a_4$: Ask client | Medium | 95% | 1 day | **Low EV** (Fallback) |
| $a_5$: Human review | High | ~100% | 4 hours | **Lowest EV** (Last Resort) |

### 4.4 Policy Optimization (The "Aggregation" Example)

The Recovery Policy Engine allows the system to fundamentally alter workflow topologies based on cost. 
For example, instead of triggering an immediate email per missing document (High Cost, High Latency), the policy dictates:
1. Evaluate $a_1$ and $a_2$.
2. If unresolved, evaluate $a_3$ (Wait for DAG completion).
3. Execute a consolidated $a_4$ (Single Digest Email) at the end of the DAG.

This is a strategic routing decision generated by Layer 3, independent of Layer 1 (Entropy).

## 5. Algorithm Selection: Decision Tree Interpreter vs. Machine Learning

When implementing the Action Selection layer, it is critical to use the correct algorithmic approach. The system will **not** use machine learning tree algorithms (e.g., CART, ID3, C4.5, C5.0, Random Forests). These algorithms are designed to *discover* decision rules from historical data. 

For the ASE Recovery Policy Engine, the problem space is fundamentally different:
* The business explicitly defines the rules.
* The tree must be deterministic, explainable, and auditable.
* Every decision must be reproducible.
* The tree must be editable via a UI by business users.

Furthermore, traditional rule engines (like Drools, CLIPS, or Jess) are overly complex and unnecessary for this use case.

### 5.1 The Solution: A Simple Decision Tree Interpreter

The MVP implementation will be a lightweight, custom Decision Tree Interpreter built specifically for ASE in Go. 

Instead of embedding raw boolean expressions (e.g., `invoice.amount > 500 && supplier.country == "US"`), the engine will rely on reusable, registered predicate functions.

```go
type NodeType int

const (
    ConditionNode NodeType = iota
    ActionNode
    TerminalNode
)
```

**Architecture:**
* **Algorithm:** Deterministic depth-first decision tree evaluation (simple tree interpreter).
* **Tree source:** User-defined business policies stored as data (JSON, YAML, or database records).
* **Condition evaluation:** Registered predicate functions implemented in Go (e.g., `InvoiceExists() bool`).
* **Execution complexity:** **$O(d)$** where $d$ is the tree depth. Evaluating ~20 boolean expressions will take microseconds, making latency effectively zero compared to LLM calls or database queries.

## 6. Proposed Changes to `ase` Package

### 6.1 Action Registry & Cost Matrix
Define a registry of available recovery actions for specific domains (e.g., Bookkeeping, OCR) along with their default Cost Matrices.

```go
type RecoveryAction struct {
	ActionID         string
	Description      string
	BaseCost         float64 // Normalized composite cost (compute + human)
	ExpectedLatency  time.Duration
	ProbOfSuccess    float64 // Historical success rate P(S|a)
}
```

### 6.2 Node State Transition (`HOLD` Interception)
When `CalculateEntropy` determines a node must transition to `HOLD`, the transition must be intercepted by the Recovery Policy Engine.

```go
// Inside node execution loop
if entropy > threshold {
	// Old: node.State = HOLD_AMBIGUOUS
	
	// New: Invoke Layer 3
	action := recoveryEngine.SelectBestAction(node, availableActions)
	return executor.ExecuteRecoveryAction(action)
}
```

### 6.3 Telemetry & Feedback Loop
To ensure $P(S|a)$ remains accurate, the engine must record the outcomes of its selected actions.
- If $a_1$ (Search document store) successfully reduces entropy, its historical $P(S|a_1)$ increases.
- If $a_1$ repeatedly fails, the engine dynamically lowers its $P(S|a_1)$, naturally routing future holds to $a_2$.

---

## 7. Analytics and Observability

The implementation of Layer 3 requires monitoring the efficiency of our recovery strategies:
* **Recovery Success Rate:** What percentage of nodes entering `HOLD` are resolved automatically without human escalation?
* **Action Distribution:** Which recovery actions are chosen most frequently?
* **Cost Savings:** Estimate the human time saved by resolving `HOLD` states via internal queries ($a_1, a_2$) versus immediate escalation ($a_4, a_5$).

---

## 8. Acceptance Criteria

Engineering is done when:
* **Separation of Concerns:** The ASE runtime explicitly separates the entropy check (Layer 1) from the selection of the recovery action (Layer 3).
* **Deterministic Execution:** The engine executes user-defined decision trees (interpreter model) using registered Go predicates rather than ML models.
* **Cost Matrix Evaluation:** A node entering `HOLD` mathematically evaluates alternative recovery actions based on cost and expected success before executing one.
* **Telemetry Emission:** The chosen recovery action, its expected value ($EV$), and its actual outcome are emitted via NATS telemetry for historical tracking.
* **Documentation:** The core actions (e.g., Document Store Search, End-of-DAG Client Request) are mapped and weighted in the codebase.
